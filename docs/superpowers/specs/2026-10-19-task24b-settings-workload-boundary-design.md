## 三 版本化配置和职责划分

新增独立的 v2 profile/plan/manifest/approval 解码分支，不在既有 schemaVersion=1 对象上默默改变字段含义。v1 的字节、hash、fileID 合同、历史读取及 fixture 保持不变；不能选择 v1 来绕过 v2 的 native 条件。现存 v1 profile 不自动迁移、覆盖或升级，同名已有根不能作为空目录接管。

v2仍使用原固定 profile 根 `D:\OpenCode-Benchmark\Task24\toolchain\docker-launch-dd479`。其中 home 固定为 `home-oc-task24-dd479`，不通过换 basename 改变预期 pipe 前缀或换成空引擎。各部分职责如下：

| 部分                            | 负责的事实                                                   | 不能做的事                                              |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| `intent.json`                   | 不可变的五个期望值、v2格式和固定策略标识/hash                | 不存秘密、授权短语或可执行能力，不随运行结果自动改写    |
| 固定版本运行策略                | 与安装hash绑定的精确文件/字段/类型/取值/临时文件规则及限额   | 不能由用户JSON、环境变量或“信任所有字段”选项扩展        |
| v2 manifest与进程内prepared能力 | 绑定意图、策略、准备种子、目录/不可变文件身份及源码/文档摘要 | 不把运行期文件身份永久写死，也不从磁盘恢复live session  |
| 运行快照与封存                  | 严格读取、检查实际设置并记录当前字节hash、语义hash和身份     | 不签发EngineSession或Linux验收receipt，不代替旧负载证明 |
| 旧工作负载门禁                  | 在启动前给出“已证明无不允许恢复”或具体blocked原因            | 不修改负载策略，不以用户确认或普通文件自报安全          |

`intent.json`的期望值固定为：SettingsVersion为44、CustomWslDistroDir为 `D:\Applications\DockerWSL`、WslEngineEnabled为true、UseWindowsContainers为false、AutoStart为false。值和类型必须同时成立，缺失值不能用后台默认值补齐。意图与派生环境、注册、原盘及固定安装共同进入 plan/approval 摘要。

v2 manifest区分三类对象：不可变文件（owner、intent及manifest自身的外部绑定）、准备种子（settings-store初始字节/hash/身份）和允许出现的运行目标。manifest不递归写入自身hash；它的hash由prepared能力和start请求绑定。授权账本与active状态继续按原有单次消费规则管理，不混为可变Docker设置，不随配置漂移删除或重建。

## 四 固定版本运行策略

### 精确目标和字段规则

运行设置目标只有以下三条，均由固定根和home推导，不接收调用方提供的任意文件路径：

1. `home-oc-task24-dd479\AppData\Roaming\Docker\settings-store.json`。
2. `home-oc-task24-dd479\.docker\daemon.json`。
3. `home-oc-task24-dd479\.docker\windows-daemon.json`。

settings-store可以在获准的窗口内发生已证明的格式化、已登记字段的合法变化以及文件替换；五个期望值和所有其他已登记安全约束必须继续满足。另两个文件也不是“任意JSON”：同样使用该安装专属的完整字段、嵌套路径、类型与值域策略。UseWindowsContainers=false不意味着windows-daemon文件可以忽略。

策略由可信适配器固定选择，绑定 launcher/backend/ASAR 等准确安装hash、格式版本、字段目录hash及临时写入规则hash。每个字段必须说明出处、取值约束、适用阶段、能否变化以及是否影响路径、联网、服务、更新、许可、编排或启动。路径类字段须解析到已批准的准确D目标；不能将字符串“以D开头”作为盘位证明。重复键、大小写别名造成的冲突、未知字段、未知嵌套键、错误类型或未证明的默认值均拒绝，不采用最后一个键覆盖前一个键的解释。

新增字段的native目录必须在真实启动前由允许的固定安装/官方源码证据补齐，不能从首次启动输出、旧C档案、未知用户配置或fixture反推。尚未证明的字段与临时文件规则明确返回blocked；不以空目录、通配规则或扩大阈值伪装完整。目录修订意味着策略hash和请求失效，需要重新审阅相应变化。

### 稳定读取与替换边界

不可变文件及全部profile父目录、home父链保持原有句柄/身份、无链接、单硬链接、规范路径和前后稳定性检查。不能因运行文件允许替换而允许父目录、owner、intent、manifest、注册、安装文件或VHD换身份。现有fileID精度条件不放宽；无法精确表示或比较时仍拒绝，本规格不夹带其算法修复。

对允许替换的目标，固定其物理父目录与相对文件名，通过绑定父目录的打开边界读取；新目标必须仍是该目录下的普通、单链接文件。运行目标句柄不能在可变窗口内一直以禁止删除共享的方式锁住而让Docker正常Rename永远失败，也不能释放父目录保护后仅按同名路径重新接管。每次采样最多重读3轮，仍受当前阶段原有轮询与总期限约束，不刷新120秒启动或30秒收尾总时限。bootstrap期间尚未产生完整文件集可保持pending到原截止时间，但不得据此签发封存；observed阶段三个目标必须全部存在且合格。稳定的非法JSON、未知字段或关键值错误立即失败，不归类为“还在保存”。

封存和每次实际用途必须取得三个目标的同组短时只读租约：保持父目录绑定，打开并固定三文件，禁止本次租约期间的写入/删除，全部取得后再复核身份、内容和跨文件约束，并覆盖该次观察的使用区间。不能将三个不同采样阶段的文件拼成完整seal；无法取得完整稳定集合则失败或在上述采样界限内重读。租约随本次用途结束释放，不长期锁住运行设置，也不以拒绝Docker合法保存来替代可变窗口设计；若固定安装不能配合这种阶段边界，native仍blocked。此处只涉及设置读取的局部租约，不修改workflow租约或重试算法。

每次快照同时记录raw hash、按明确策略生成的semantic hash、文件身份、策略hash、意图hash、进程内阶段与序号。raw hash用于封存后检测任何变化；semantic hash用于窗口内验证允许的格式差异与内容约束，不能跨阶段取代raw hash。字段目录中的动态值也必须有具体类型/范围约束，不能全体删除后再算“相等”。

本设计允许的是可信本地控制器管理的受限变更窗口，不声称能证明每一字节一定由某个PID写入，也不抵抗同SID恶意代码或管理员。若实际兼容判断要求更强写入者归属，须先补充获批的文件I/O来源证据；不能把“PID正在运行＋文件在D盘”当作来源证明。读取校验是检测能力，不是拦截一切文件写入的沙箱；完整路径和自动行为门禁仍必须在启动前满足。

### 限额

提出以下校验与接纳上限供本规格审阅：intent最多16384字节；每个最终运行设置文件最多1048576字节，三文件合计最多3145728字节；JSON嵌套深度最多32。临时写入只接受已证明与这三目标对应的准确命名规则，最多同时3个临时文件、每个最多1048576字节；拟接纳的设置最终文件加临时文件总量上限为6291456字节。超限阻断，不自动上调。

临时文件的准确命名规则目前未被完整证明，因此限额本身不能启用native规则。不得拿`*.tmp`、整棵home或允许任意新文件替代该证据。文件校验不是文件系统硬配额，不保证尚未观测到的短暂峰值或事后发现超限前从未发生写入；native放行还须有前置证据约束输入与实际写入，不能仅靠启动后抽样宣称保证预算。上述只覆盖设置相关payload，不含NTFS分配、日志、其他应用输出或VHD增长；其他写入未闭合时，完整启动写入预算仍不成立。

## 五 受控生命周期与失败收尾

| 阶段                 | 设置检查                                                                   | 可接受的变化                                                       |
| -------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| prepared及启动前确认 | 意图、不可变文件和准备种子的准确字节/hash/fileID；另两目标应不存在         | 无Docker写入；未知已有目标拒绝接管                                 |
| starting             | 消费当前start许可后，由当前控制器打开bootstrap窗口，验证固定运行策略与身份 | 仅三个目标和已证明临时文件的策略内变化；不增加其他系统权限         |
| observed             | 取得稳定完整快照后封存全部raw hash/fileID；每次CLI/存储观察前后复核        | 不自动吸收后台变化；漂移阻断继续使用和成功结果                     |
| stopping             | 仅当前已消费stop-owned能力可打开有限收尾窗口                               | 仅已登记的退出保存规则；不得更改关键值、忽略未知字段或延长30秒上限 |
| stopped或stale       | 关闭窗口，记录最终状态；下次操作重新审计                                   | 不恢复live能力，不自动续跑或重新封存漂移文件                       |

窗口必须绑定当前进程内session、准确安装/进程归属、intent/policy/plan/manifest、阶段和剩余时限。磁盘记录、历史seal、复制对象、caller传入的时间或stage字符串不能打开窗口；后台正常修改也不能自动延长窗口。如果某个固定版本确需在observed阶段继续写入，当前策略仍拒绝，另行审阅精确行为，而不是改为整个session永久可变。

**使用资格与收尾资格分开。** 关键值变化、未知字段或设置损坏应立即阻断新的CLI、存储证明及成功交付，但不能因此丢掉已获准、仍可验证归属的finally收尾。停止仍使用消费时保存在内存中的准确目标和已审核通道，重新核对PID/创建时间/SID/映像/pipe归属；不从损坏设置读取新endpoint，不要求配置先恢复正常。保留现有“start许可到期不取消本次已消费收尾资格”的规则。

归属、停止方法或身份不明时返回cleanup_uncertain，保留原始失败与收尾失败，列准确残留；不按名称强杀、不停止既有服务、不全局shutdown、不恢复设置或旧盘数据。进程崩溃后的记录不能恢复stop权限。即使停止成功，运行设置不合格的原始操作仍是失败，不改报成功。原生安全收尾链未证明时，启动继续为0次。

## 六 与存储观察的接缝

新v2观察上下文分别携带intent hash、策略hash和当前runtime seal；准备种子hash不再冒充运行时settings hash。新decoder必须同时核对当前v2 session、稳定运行快照、关键设置值、manifest、原注册和VHD身份，以及原有的实际设备/UUID、daemon身份和swap观察链。不能仅凭settings-store里写着D路径就出具活动盘证明。

保留v1 decoder及旧StorageSource分支的校验。v2在明确版本化的内部上下文中处理新的hash语义，不混用旧snapshot；公开StorageProof/HostRequest等结构不因本设计增加一个可自报的“已通过”布尔值。其settings摘要如继续使用现有SHA256字段，必须明确绑定当前intent、策略、runtime seal和实际观察的canonical数据，不塞入准备时的旧hash或不同含义的值。

旧的default/endpoint/daemon一致性断言不放宽，`production_default_compatible=false`仍阻断相应生产接入；不顺便修改生产docker-config。inventory最多为inventory_observed_not_accepted或blocked，engine_verified、tool_capability_verified、corpus_engine_ready继续为false，不签发Linux验收凭据。

## 七 旧工作负载风险门禁

### 默认拒绝与覆盖范围

门禁回答的是“启动原daemon/后端是否可能引起当前阶段不允许的既有工作负载恢复”，不是“本控制器有没有调用docker run”。覆盖原盘中的容器恢复状态及策略，以及相关Swarm、Kubernetes等编排器可能重建的任务；不能以所有已知容器的某一字段为no，就忽略尚未排除的编排范围。官方也区分容器restart policy与Swarm服务策略。[Docker恢复策略范围](https://docs.docker.com/engine/containers/start-containers-automatically/)

结果只分为已证明满足边界，或带具体原因的blocked；没有“用户已确认所以安全”“默认放行”“风险已接受”旁路。当前原盘没有所需可信证据，native结果继续包含existing_workload_restart_unproved。AutoStart=false、UseWindowsContainers=false、WSL running为空、服务存在、VHD存在/大小不变、用户口头说明、安装静态函数或普通JSON均不能关闭它。

该门禁必须先于native兼容成功报告、可执行profile准备确认和任何Desktop/backend/daemon启动。fixture可验证门禁逻辑，但fixture证据不能注册为native；不提供环境变量、自报assurance、注入transport或通用回调作为真实放行入口。

### 未来证据的必要条件

将来若另获取证方法及操作授权，证据至少须绑定准确安装/引擎版本、原注册、原VHD路径/fileID/volumeID、完整检查范围和明确无歧义结论，并证明所检查的内容状态在启动消费前没有改变。fileID、size、mtime相等只能帮助发现部分漂移，不能单独证明盘内负载内容和策略未变。证据获取时持有的稳定性保护与最终启动前再验证必须可审查；方法不能把不允许的恢复发生在证明完成之前。
