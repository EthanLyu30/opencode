## 三 什么才算补上厂商契约

厂商契约可以是公开的准确接口与实现，也可以是用户获准取得并允许本地使用的厂商技术答复。后者必须有可核实的官方来源、适用构建和明确行为保证；论坛建议、营销页、AI答复、笼统“支持WSL/只读/停止”不够。保密材料是否可进入Git是另一项授权，默认不进入仓库、不上传；用户提供的原件不删不改，只在允许范围内引用脱敏结论与来源元数据。

不强求接口名称叫 reserve/commit/abort，也不要求把第三方真实API改造成自定函数。**需要厂商提供等价、可审查的行为保证**：

| 契约义务          | 必须回答的具体问题                                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| K1 连续保护       | 如何从现有OPEN_EXISTING、只读、禁止写/删除共享及父链保护，连续交给准确writer，不先关锁再按路径打开？不预拿可写原盘句柄           |
| K2 准确身份       | controller/request/nonce如何绑定进程句柄、精确创建时间、SID、映像及本次VM？不能只凭PID、pipe名、首个请求或UserToken              |
| K3 双盘整体准入   | 两盘是否共同保留、验证、提交？第一盘不能在第二盘保护/归属未完成时先获可写接管。两个attach调用或“VM暂不运行”不自动等于VHD未被写入 |
| K4 并发与既有状态 | 如何排除其他正常竞争writer、已有可写mapping、父链替换和多请求？适用文件系统/打开参数/拒绝条件是什么？                            |
| K5 全异常分支     | 取消、超时、第二盘失败、controller/持锁者/消费者崩溃时分别怎样回到安全状态？是否有界？不能以恢复/回滚原盘内容收尾                |
| K6 晚到请求与归属 | 取消完成后等待writer能否继续？如何完整join/撤销，仅收尾本次资源而非停止共享SYSTEM服务/外来VM？                                   |
| K7 构建与依赖     | 哪个Desktop/backend、WSL/HCS、Windows/FS版本及打开参数实现上述保证？有何启用条件、修复版本/已知限制？                            |
| K8 当前边界兼容   | 是否要求升级、补丁、驱动、ACL/share/服务变化或可写原盘预取？如需要，即非现有边界内可用方案                                       |

K1–K8回接HS的O1–O8及C1–C10，不删减反例。共享/权限/签名/hash、退出HTTP成功、单盘LUN清理、内部VM锁均不能补足端到端保证。未提供取消后的终止语义或双盘保证，即使名称、版本齐全也不合格。

### 厂商材料的有限取得方式

未来第一个可另批小包仅为“新材料接收/公开来源裁决”，不读本机安装：

1. 优先接收用户指定的新官方材料。没有新线索时，最多一次收口式公开检索，最多2条准确版本/交接主题查询；实施计划先写定查询和来源入口，不重复HS同义搜索。
2. 仅Docker/Microsoft官方文档、官方项目、准确发行说明或可验证厂商答复；最多8份文本材料，每份实际响应不超过2097152字节、合计16777216字节。网页/源码仅内存读取，记录时间、版本、位置、表示形式和实际摘要，不保存整页/完整源码缓存，不下载安装包、符号包或归档。
3. 仅跟随明确新协议的直接定义，计入同一8份限额；不自动追间接引用、全仓库、无限历史版本。未能先指明准确文件/commit就把它列为缺项，不用符号末尾/模糊正则找同名函数。本包不新增PE反汇编。
4. 网络失败同一来源最多重试一次；没有合格契约、达到预算或需要新范围即交付明确blocked并停止，不自动进入目标采集。需账户、付费、保密文档或非文本转换时先另行确认，不登录/购买/转换来绕过。

若公开材料不足，可交付**未发送的厂商技术问题稿**，不是自动开展外部协调。建议分别向Docker确认入口/整体生命周期、向Microsoft确认WSL/HCS消费及异常保证；回复需能连成一条链，不能把互不负责的两段答复拼成整体承诺。没有联系权限或回复就是待厂商材料，不通过定时反复搜索保持“进行中”。

发送问题、开issue/支持单、登录或支付支持费用，以及上传任何本机资料，各自需新授权；默认问题稿只含公开版本和抽象两盘场景，不附本机路径、文件身份、账号、日志、环境或Key。即使收到官方回复，也先验证其来源/适用性，不把回复当运行许可。

## 四 版本对应不是“一串版本号”

需要建立有出处的链：**目标静态身份 → 准确官方发行/构建 → 交接实现或有责任范围的版本契约 → 全部适用条件**。每条边独立记 proved/unknown/contradicted，记录依据及反证；任一unknown不得汇总成proved。

| 目标            | 未来须取得的最少材料                                                                                   | 明确不能替代的东西                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Desktop/backend | 原七成员再核一次、准确构建/映像摘要，以及厂商对该构建的协议支持/实现映射                               | PE里有同名符号、componentsVersion.gitCommit或CLI版本不能直接映射闭源源码        |
| Windows         | OS Version/BuildNumber/Architecture；如契约依赖补丁修订，还需准确修订来源和相关系统组件对应            | “Windows11”/最低支持版本/注册表一个值不能证明实际组件均已生效                   |
| 宿主文件系统    | 指定D卷的文件系统名/必要能力标志，及后续原盘真实落点的独立证明                                         | D盘符、NTFS名称或某个事务能力flag都不能证明两盘交接；宿主FS与VHD内ext4分开      |
| WSL             | 安装渠道、准确包/服务入口和所需消费者文件摘要，固定release/tag解析到immutable commit；厂商构建对应材料 | Docker WSLBootstrap不等于安装WSL；公开master、release标题或签名不等于本机消费链 |
| HCS/实际消费方  | 厂商点名的系统组件版本/文件与协议实现对应；若实现闭源，需厂商覆盖该构建的明确保证                      | WSL源码调用HCS、AddVhd按路径传入或generic API存在不能补齐HCS内部保证            |

不要求不存在的“所有二进制可复现构建”才能记任何事实，但也不把一个release tag当二进制→源码证明。开源构建可用官方manifest/构建证明建立对应；闭源组件可以依赖可核实且覆盖准确构建的厂商契约。无任一可信桥接就保持该边unknown。

发现结果只形成下一次待审的**准确路径清单**。即使返回路径指向C系统安装，也不得在同一批准下打开该目录/文件、查版本资源或hash；不得把InstallLocation/PathName当可信可执行指令。候选路径的规范化/重解析策略、普通文件和父链检查均须在后续文件读取计划中定义；当前不去探测路径是否存在。

WSL若不在上述包/服务渠道中、必须查询其他注册位置或旧系统组件，先报告未知渠道及所缺证据；另立准确发现范围再确认，不追加MSI注册表搜索或全盘查找。源代码缺边也同样停止，不将新commit/文件自动加入清单。

## 五 后续工作包与硬停止门

以下是拟议顺序，不是本轮执行任务，也不是NW续号。每包可独立交付有限报告；前包通过不自动授权后包。

| 包                     | 内容与交付                                                                                             | 继续条件 / 失败处置                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| CV1 契约线索裁决       | 固定新厂商材料、K1–K8及HS O/C缺口映射；必要时未发送的问题稿                                            | 无具体协议线索/明确冲突即blocked停止；不为了搜集更多版本转入CV2                                                       |
| CV2 最小身份发现       | 按单独批准的V-OS/必要V-PATCH/V-FS/V-WSL-PKG/必要V-WSL-SVC字段，形成版本记录和待审路径清单              | 有可信机制线索才申请；若厂商明确先要版本信息，须用户单选“仅CV2最小字段”，不视为CV1已通过。未知/超时/歧义/需提权就停止 |
| CV3 准确文件与来源映射 | 根据CV2及厂商点名材料，先呈现准确路径/文件/版本/大小/工具/预算，另批后才读；输出安装→发行→协议逐边矩阵 | 路径/文件未批准不读。backend或WSL到实现缺边即unknown；不自动扩到其他映像/构建                                         |
| CV4 静态封口           | 逐项复核K1–K8、HS O1–O8/C1–C10及目标对应，输出有界结论/未取得材料/下一授权                             | 缺证即blocked；全部静态证据齐也仅候选待验证，运行仍blocked；不继续实验/reader/layout/NW                               |

普通CV1→CV2门槛不是“看到一个相关名称”：K1–K6及K8须已有原始厂商语义/实现依据，且HS机制反例无未决项，仅K7的本机版本适用性等待最小采集。机制本身仍缺关键保证时，CV1即blocked，不借采集版本向前推进。为厂商明确索取版本而单选的CV2是独立信息包，不把CV1改为通过。

CV1→CV2的特殊分支只为厂商明确需求/准确版本定位，不允许“只要契约难找就扫描本机”。用户可只批准公开材料包，或只批准最小发现包；任一包不成功，有限报告就结束，不无限保留活动研究状态。

### 文件读取、时间和输出的后续预算上限

未来CV3的七成员复核仍准确沿用HS七路径，单文件268435456字节、1MiB流式buffer；七成员合计最多536870912字节、一次完整复核。漂移即 `static_target_drift`，停止，不自动适配新安装；不是请求实际读原VHD。新增系统/WSL文件**最多8个、每个67108864字节、合计268435456字节**，每项须事先列准确路径、大小来源和读取目的；大小未查明时只能先申请该准确文件的元数据，不先读内容。超过上限需要新的明确范围，不能边读边扩大。

## 六 裁决规则与证据新鲜性

后续文档逐条列 `claim / target / source revision / acquiredAt / representation / sha256或缺失原因 / location / supports / limits / status`。厂商来源真实性、精确构建适用性、静态机制义务、实验和当次盘事实分层；普通JSON、报告签名/hash和时间戳不产生能力。
