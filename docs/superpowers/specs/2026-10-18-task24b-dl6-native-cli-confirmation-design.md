后续 native 请求的文档摘要必须覆盖本增量：`DesktopLaunchSpec.specSha256` 取基础规格和本文的 `{path, sha256}` 清单的 canonical JSON hash；`DesktopLaunchSpec.planSha256` 同样绑定原计划和获批补充计划的清单。数组按仓库相对路径排序，内容 hash 基于实际文件字节。`sourceSha256` 继续绑定实际源码状态；旧单文档摘要不得继续使用。这两个文档摘要与 `DesktopLaunchPlan` 中另行计算的请求 spec/profile plan 摘要区分，approval 仍绑定实际 profile plan 和兼容报告。兼容授权摘要只包含可重算的证据和规则，不混入每次变化的采样时间、探针 PID 或临时目录 nonce；这些放入独立诊断快照并另行校验时效，避免用重新签发请求掩盖真实漂移。

接入已经能够验证的离线 CLI 查询，不再永远用固定占位文字代表其结果。只运行已核身份的准确 CLI、固定 `context inspect default` 参数和隔离 D 配置来源，不读用户配置、不接触 daemon；返回码、输出上限、编码和查询前后身份都必须验证。不能接受调用方提供的所谓真实查询输出。

`cli_default` 的证明是正确刻画两种连接字段的解析行为，不要求两个地址相同。生产默认地址与 profile 地址不同，继续输出 `production_default_compatible=false`，阻断后续生产接入/A组合同；它不被包装成整个原生审计失败的唯一原因，也不授权修改生产连接。上次仅观察到地址差异，未证明两个地址一定对应不同 daemon。

### 无启动观察

原生只读观察区分主机事实与本次 session 归属：

- 从实际 Windows 身份读取当前 SID，并将真实 profile 与现有 WSL 配置绑定；不从 `USERNAME` 或伪造的 D `USERPROFILE` 推导真实用户。
- 只读查询进程创建时间、SID、准确映像和父子关系；相关 PID 必须与同次观察的身份一致。无权限、进程退出或快照冲突均不能解释为安全 idle。
- 读取白名单注册字段及两块 VHD 的路径、fileID、volumeID。注册 State 不是运行状态；VHD 不读盘内数据或整盘 hash。
- WSL 状态仅由固定系统工具的 list 查询取得，严格处理实际编码、状态和歧义。不执行发行版内命令，不用查询某个发行版的方式将它暗中启动。
- 既有 `com.docker.service`、WSL 服务和计算系统服务不自动归属本次；服务正在运行不等于 Docker engine 正在运行，也不等于它会继承本次环境。
- 启动前只检测相关管道和进程冲突，不向未知实例发 API。需要连接管道核对 owner 或读取活动存储的观察，仅在另获真实启动授权且持有本次 live session 时执行。

未知观察返回具体缺项，不能伪造 `phase=idle` 或 `runningWsl=false`。内部可保留严格解码的诊断快照，供当前控制器作决定；磁盘 JSON 和命令输出不能恢复 live session、停止权限或存储证明。

### 固定且有界的系统边界

系统辅助程序使用准确路径、固定操作和严格数据输入，不提供自由 shell、argv、URL、脚本路径或任意管道名。子进程隐藏运行，最小环境不继承 provider、Electron、WSL/E2E 或 Docker 注入字段。输入、输出、单次等待和总等待均有界；超限、取消或辅助程序失败立即关闭相关能力。

复用当前文件身份和发布保护，不将“检查后按路径再打开”当成足够的替换防护。需要实际启动/控制时，准确映像、句柄和身份须在关键操作处保持绑定；不支持这种绑定的平台返回 blocked，而不是降低校验。

## 交互式 CLI 确认

### 命令和控制输入

原有 `audit`、`plan`、`inspect`、`stop-owned` 语义不变。对 `prepare-profile` 和 `start-readonly` 增加显式布尔开关 `--interactive`，无重复形式、无 `=true` 形式；没有该开关时仍拒绝副作用，不自动弹窗或转入交互。

准备和启动均继续显式提供 `--spec` 与 `--approval`。`approval` 文件只是待核对的操作请求，不是许可；不增加 `--yes`、环境变量授权、保存密码、历史同意复用或 unattended 模式。

native 控制输入固定在 `D:\OpenCode-Benchmark\Task24\control\desktop-launch\<launchID>`，其中 `spec.json` 对应本次准确 spec，`prepare-approval.json` 或 `start-approval.json` 分别对应操作。各请求只读取本次文件，不搜索整个目录。合成测试使用既有 D 盘 owner 根下的对应布局，不能通过测试入口指向真实根。

所有输入沿用有界、稳定、严格解码及逐级无链接检查。控制文件不读取环境秘密、不复制到 Docker 子进程。上述控制目录和文件本轮不创建；未来真实准备清单必须同时列出它们，而不是只列 profile 内部4个文件。

### 确认前核对

先严格解析参数和请求，重新审计安装/真实观察、计算当前 plan，并核对请求的阶段、SID、目标、plan/compatibility hash、注册、VHD、有效期及所需 manifest。只有这些前提成立才显示可确认提示。普通确认不能把 blocked 变成 ready。

现有 native 兼容仍有缺项时，命令只输出缺项并退出，不索取一份明知无法执行的“先同意再说”。准备不要求尚不存在的 manifest；启动必须绑定实际已准备的 manifest。对不匹配的请求不自动刷新时间、换 nonce 或代填摘要。

确认面板显示操作名称、真实 SID、launchID、准确目标目录、源码/文档摘要、请求 spec/profile plan/compatibility 的 SHA256、当前安装身份，以及注册和两块盘身份。准备面板列新增目录/文件、五个设置值和发布空间预算；启动面板再列 manifest hash、准确程序/argv、D 环境白名单、观察范围、输出位置、启动120秒和收尾30秒上限及停止方法。不可证明的 argv 或停止规则不能作为候选默认值展示。

提示使用可信固定文案；外部文本不得注入终端控制序列、伪造行或双向文本覆盖。显示失败或内容被截断时拒绝确认。完整必要信息展示后才生成本次确认短语。

### 本地控制台和一次性确认短语

准备/启动要求本地 Windows 控制台的 stdin、stdout、stderr 都可交互；使用实际标准句柄的 console 能力核验，不只看环境变量或一个 `isTTY` 布尔值。管道、重定向、无控制台或不支持的终端均拒绝；不另开 `CONIN$` 绕过已重定向的 stdin。Windows 标准句柄可以被父进程重定向，因此句柄存在本身不证明是控制台。[Console Handles](https://learn.microsoft.com/en-us/windows/console/console-handles)、[GetConsoleMode](https://learn.microsoft.com/en-us/windows/console/getconsolemode)

确认面板写 stderr，最终有界 JSON 写 stdout。每次提示从系统随机源产生至少96位的独立 challenge，并与本次规范化请求、面板内容 hash、阶段和控制器实例绑定。用户必须输入形如 `PREPARE <launchID> <challenge>` 或 `START <launchID> <challenge>` 的完整短语；只有准确匹配的一次输入可继续。空输入、通用 yes、错误短语、额外行、EOF、Ctrl+C 或等待到期都取消，不循环猜测，不回退为 JSON 同意。

提示最多等待60秒，且不超过请求剩余有效期。等待期间不消费 nonce、不创建 profile、报告或授权文件、不启动程序。测试时钟和模拟控制台不能用于 native 入口解除门禁。

这是防止误执行、非交互调用和普通文件伪造的操作确认，不是抵抗同 SID 恶意程序、管理员或可注入控制台输入进程的密码学人类认证。只有原规格指定的可信本地控制器可签发进程内能力；不存在安全的“从键盘字节证明一定是真人”的承诺。

### 确认后的再验证和能力消费

确认只对当前冻结快照有效。接收短语后、消费 nonce 前，重新核对安装、文件/父目录身份、manifest、注册/VHD、当前 SID、有效期和进程/WSL/管道冲突；若影响授权的内容变化，整次取消，不静默更新面板或套用旧输入。

通过后沿用现有 `confirmDesktopApproval` 的进程内来源登记、严格阶段检查、最长15分钟有效期和 D 盘一次性 nonce 消费。普通文件和新进程不能恢复能力。消费后失败或崩溃也不自动重试；重新执行需要新请求、新 nonce 和新的本地确认。

native 控制器只接受其可信 console 工厂在当前进程签发的确认来源，不能把任意传入的 `async () => true` 回调视为许可。通用嵌入回调可保留给 fixture 测试，但与 native 来源隔离；生产工厂不开放替换 transport、模拟控制台或绕过来源登记的开关。底层 prepare/start 及授权校验也须核对此来源，不能只在脚本中检查，留下直接调用导出接口的绕过路径。测试复用同一校验逻辑不等于获准注册真实能力。

准备确认不含启动。启动确认包含本次已归属资源的 finally 收尾，不在异常期间再索取一次停止确认；未获真实启动授权时不能提前消费启动请求。新进程的 `stop-owned` 不凭 launchID 猜测接管残留。

## 设置和应用自动行为

独立五字段设置、manifest 和文件身份继续使用现有严格校验。本增量不将整个设置文件改成“只要五字段还在就接受”，不把 Docker 初始化新增字段、原子替换或自动修复当成可信修改。若固定版本启动会重写该文件，且与现有合同不相容，启动前保持 `settings_mutation_unproved`；需要支持可变设置时另提最小设计，不在实现中暗改。

最小子进程环境新增明确的 `PINATA_SINGLE_INSTANCE_LOCK=true`，并纳入 plan hash、面板及回归。固定安装资源已显示 home override 默认可绕过前端锁，详见原生证据报告。该字段只解决同 profile 重入，不替代全机进程、管道和 WSL 冲突检查，也不证明后端完整生命周期隔离。

`AutoStart=false` 不当作禁止容器恢复、自动升级、许可弹窗、后台下载或系统服务写入的总开关。凡这些分支未能在固定安装上证明符合保护边界，保留具体缺项；不自动同意许可、提权、改服务或下载。

尤其是复用旧数据盘：Docker 的 restart policy 可在 daemon 重启后恢复旧容器。因此“未发送 docker run”不等于“没有启动容器”。当前未知旧盘工作负载策略时保持 `existing_workload_restart_unproved`，不能试启动后再检查，不读挂载旧盘来绕过当前权限，不擅自改容器策略。如果现有边界下不能证明安全，须向用户说明并另议操作范围，不能靠输入 START 短语豁免此项。[Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/)

上述额外缺项可作为现有兼容报告的 missing 值表达；不通过新增自报布尔开关绕过五项整体门禁。

## 启动和停止能力继续封闭

本规格不认定现有安装已具备可启停条件。原生 start/stop 实现只有在准确入口/argv、全链路 D 路径与环境、原注册/盘发现、设置行为、自动行为和作用域正确的停止链均有可复查证明后才能启用；在此之前保留显式拒绝，不以待测试的猜测填空。

原生进程归属需由当前工厂在实际启动时登记，并与现有不透明 session 一同保持在内存中。请求提供的 ProcessIdentity、克隆对象、PID、静态报告或磁盘记录不能获得停止权。管道的实际 server PID 还须连同创建时间、SID、准确映像和归属链验证；API 给出 PID 不代表完整归属证明。[GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid)

停止只用已证明作用域的本次专用控制通道，并在发送时绑定同一目标身份。候选 `/app/quit` 仍需证明完整后端/引擎/WSL 收尾范围；HTTP 返回不等于资源已停止。观察冲突、身份改变、超时或归属不明时输出 `cleanup_uncertain`，列准确残留，不按名称强杀，不停既有服务，不调用默认 desktop stop 或全局 WSL shutdown。

原规格启动120秒、收尾30秒的总上限保持不变，固定查询各有更短上限；取消不解除归属检查。控制器崩溃后只能读取 stale 记录，不自动重启或恢复执行/停止权。

因此本增量可能交付“真实只读诊断/观察和交互确认已实现，native 启动仍因具体证据缺项关闭”。这不是完整原生生命周期已可用，也不算 DL6 真实环境核查通过。
