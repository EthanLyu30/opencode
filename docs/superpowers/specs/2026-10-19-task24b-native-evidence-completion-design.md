## 一 目标与当前结论

## 三 证据必须能回答什么

每份候选记录固定：待证明命题、适用 Windows/文件系统/WSL/Desktop 版本、源码 commit/文件位置或厂商契约、来源与实际字节摘要、依赖/许可证、已知反例、拒绝条件及验证结果。未知版本或来源明确记“未取得”，不能填零 hash、用 latest 或符号名字凑齐。

证据分为三个层级，不混写为通过：

1. **静态候选**：存在准确接口/代码和适用条件，但尚未证明整条链。
2. **实验合格**：在另批的自有 D 合成数据和 helper 上验证了真实机制，具有可重复的反例与拒绝回归；没有操作安装的 Docker/WSL。
3. **目标适配有依据**：固定目标版本确实使用同一机制、参数、布局和归属链，不是把合成 helper 的成功当作厂商实现成功。

合格规则必须同时具有完整证据和适用性；不得从本方案、候选 JSON、网页、签名文件、测试 exit0 或历史报告恢复任何能力。目标原盘身份/内容的当次事实仍须后续正式软件在独立授权下取得，不塞进静态 descriptor。

## 四 安全交接先行

### 要验证的安全不变式

从双盘完整受保护采集开始，到准确本次 writer 获准工作为止，两盘及父链不出现外来修改或身份替换。只有当前 plan/request/nonce/controller 对应的 writer 可以接管；其身份至少绑定进程句柄、精确创建时间、SID、映像摘要和本次 VM/控制链。共享 SYSTEM 服务的存在，不使整项服务成为我们可停止或接管的资源。

必须覆盖两盘的整体交接，不能第一盘已经可写，第二盘仍未完成保护/归属核对。确认“writer 接管”须有真实机制保证，不能以 PID 出现、pipe 存在、打开成功或 HTTP 退出成功替代。

读取期继续遵守既定 OPEN_EXISTING、只读、禁止写/删除共享及父链保护；不为研究方便预先取得原盘可写句柄。需要改变这些条件的候选先标为超出现有范围，不在实验或代码里悄悄替换。此前只读锁持续到普通 callback 返回的 fixture 不能直接当原生方案。

### 按有限候选逐项审查

| 候选                          | 具体要查的证据                                                                                                                           | 不足时的裁决                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 厂商支持的交接/分阶段写入准入 | 固定 Desktop backend → WSL/HCS → 双盘 writer 的接口链；是否接受受保护对象或提供可绑定 writer 的保留/提交协议；失败、取消及完整已归属收尾 | 没有准确契约和目标版本对应实现就 blocked，不自行注入、改二进制或模拟成功                               |
| Windows 句柄交接              | 与目标兼容的访问权、共享规则、双盘原子性和消费方支持；不是只验证 DuplicateHandle 调用能返回                                              | 只读 handle 的复制/重开不能据此推导可写接管；目标仍按路径独立打开而无协议就不合格                      |
| 文件系统 oplock 等机制        | 固定文件系统/锁类型/全部 break、ack、映射写入、异常 create 选项、持有者崩溃和多 writer 行为；必须绑定真正的破锁请求及本次 writer         | 仅有 break 通知/AccessMode/ShareMode 不足；无法识别准确请求、无需 ack 的分支或失效时无安全收尾就不合格 |

Microsoft 明确说明只读文件 handle 不能通过 [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)变为兼具读写权限的文件 handle；[ReOpenFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-reopenfile)也不能请求与尚未关闭句柄的共享条件冲突的访问。因此，这两者不是已经找到的解决办法。

[oplock 输出结构](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-request_oplock_output_buffer)列有锁级别、flags、access/share mode，未提供足以直接认定本次 writer 的 PID/创建时间/VM 身份；[破锁规则](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/breaking-oplocks)还区分是否等待 ack、特殊 create 选项及持有者退出情形。**据此推断：oplock 最多是待审候选，不是可直接替换现有保护的安全锁。** 不以无限期不 ack 阻塞外来程序，也不能在取消/崩溃时仅关闭句柄就假设等待中的 writer 不会继续。

[公开 WSL WslCoreVm.cpp](https://raw.githubusercontent.com/microsoft/WSL/master/src/windows/service/exe/WslCoreVm.cpp)可定位 `AttachDisk/AttachDiskLockHeld` 和 `AddVhd` 相关路径，但 master 不是本机 WSL 的版本 pin，内部 VM 锁也不是已证明由外部控制器持有的双盘交接协议。后续须先取得本机安装构建与准确源码/契约的对应关系；无法对应就是缺项，不执行 WSL 来“试一下”。

### 交接的接受与最早停止条件

先交付有限三类候选的适用性/反例表、完整调用和所有权链、每一步仍生效的保护，以及取消/超时/控制器崩溃后的实际状态。只有存在满足既定边界的候选，才值得另行计划自有文件与竞争 writer 的实验。

实验的反例至少包括：提前解锁、多 writer 同时请求、两盘取得/移交部分失败、同 PID 换进程、伪 pipe/VM、超时后晚到写入、已存在映射和持有者崩溃。任何未批准 writer 可写、取消后仍可能继续且无法安全收尾、必须先更改共享/ACL/服务规则、或仅有自制 helper 而没有厂商兼容依据，均不合格。

如果这些候选都没有可信实现，**停止交接启用路线，并保持另外两项为待补证，不继续下载/实验或推进 NW2–NW13**。输出准确缺少的厂商接口/版本/行为保证；可以草拟供应商技术问题清单，但不自动发消息、开 issue 或提交数据。无新来源时不无限重查相同 API。交接有依据是继续研究的必要条件，不是启动许可。

## 五 完整布局如何闭合

交接具备可信静态候选后，先建立准确安装的启动与存储关系，再决定读取器需要支持哪些格式。允许先形成“候选布局”，但未闭合的范围永远 unknown，不能先判空。

未来静态取证清单须精确列出安装成员、内置启动资产/配置及可读范围，并记录 hash；不泛读 D 盘、不执行或挂载这些资产。由 launcher/backend 设置和启动分支，追到 WSL/runtime 引导、实际 daemon/containerd 参数、存储映射和自动激活来源。闭源分支只找到字符串/符号时仍不足，不用公共 Moby/containerd 默认值覆盖厂商可能修改的行为。

| 必须闭合的范围    | 布局目录应固定的内容                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| 启动/双盘映射     | 两盘各自作用、挂载/映射链、路径跳转与每条可达启动分支；初始化、导入、升级、备用路径的启用条件                    |
| daemon/containerd | 实际组件版本、全部实例、root/state/socket、可激活 namespace、存储模式及配置覆盖来源                              |
| containers/tasks  | 全部注册/索引/沙箱/可恢复执行对象的格式与权威位置；停止对象、残留索引和多实例均计入                              |
| Swarm             | 成员身份、持久控制状态、本地任务及重新加入后接受远端任务的可能性；不能只数本地 task                              |
| Kubernetes        | 每个 provisioner、静态工作负载、控制状态与设置/默认自动 provision 的组合；未知 etcd/secret 内容不解码兜底        |
| 其他激活来源      | Desktop 扩展、模块、引导服务/计划、宿主后台客户端、外部挂载或其他可恢复/新建任务的来源；逐项证明不存在或完整覆盖 |

[Docker daemon 文档](https://docs.docker.com/engine/daemon/)说明 data-root 不涵盖所有 containerd image-store 数据，这只证明必须核查分离存储，不能证明本机实际路径。仅镜像/卷/缓存不自动等于负载，但与激活来源的关联未排除时仍拒绝。

布局合格必须给出可达来源全集及逐条排除/解析证明，而非“扫描几个常见目录没发现”。碰到第三盘、外部 journal、差分父盘、未知 namespace、未知数据库/加密或路径依赖，不跟随、不跳过，不将 unknown 当零。

宿主客户端或远端编排触发不能仅凭盘内索引排除，须由单独的环境/自动行为/控制链证据支持；盘空不代表启动后不会被创建任务。本轮不因此调用运行期 CLI 或检查旧 C 配置，取不到必要证据就保留相应门槛。

如果准确布局只能通过原 VHD 的引导或配置内容才能确定，列出这项证据依赖并停止静态闭合。**不能因为需要布局而先扫原盘，再用扫描结果补写允许读取集合。** 后续须另立准确且有界的引导取证方案和正式权限链，单独申请内容读取；若连可允许的最小读取范围都不能预先确定，则当前路线继续 blocked。本文不预授权这种引导取证，也不绕过 NW2–NW13 造一个能读原盘的研究脚本。

产物是固定版本布局目录及支持范围/拒绝表；候选 Linux 路径只在取得来源后登记，不在本文编造实际路径。静态布局规则合格与“真实旧盘匹配且为空”是两件事，后者必须等独立读盘授权和当次事实。

## 六 读取器如何取得资格

读取器不是下载一个磁盘工具就完成。推荐先审查成熟解析能力的组合，暂以 libvhdi + TSK 为候选；不锁定采用、不下载、不宣称已合格。若组合不能满足要求，输出缺口，不临时拼接通用恢复器或无限扩展候选库。

| 层       | 候选接口与补证重点                                                                                                                                                                                  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VHDX     | [libvhdi 头文件](https://raw.githubusercontent.com/libyal/libvhdi/main/include/libvhdi.h.in)的 bfio handle/offset read/abort；核对完整打开链、父盘/日志/恢复分支，不暴露路径打开能力                |
| 文件系统 | [TSK image 接口](https://raw.githubusercontent.com/sleuthkit/sleuthkit/develop/tsk/img/tsk_img.h)的 external read callback；按已闭合布局审查分区、ext4 特性和选择性 metadata 解码，不直接跑通用 CLI |
| 索引     | 仅支持布局目录要求且已固定版本的索引格式；根据真实布局选择解析能力，不预假定某个 DB/键即可表示全部负载                                                                                              |
| 调用边界 | 可信 broker 持有只读双盘句柄，读取器仅有有界 ReadAt；禁自主打开主机路径、写入、挂载、外部父盘、回放、修复和执行盘内程序                                                                             |

[libvhdi 实现](https://raw.githubusercontent.com/libyal/libvhdi/main/libvhdi/libvhdi_file.c)拒绝写访问是有用线索，不证明整个组合的无写入、无额外打开和一致性保证。若原生库必须获得能自主开文件的通用句柄或不受约束的路径，则不能据 API 名称签发资格。

### 固定供应链与无 Docker 验证

源码及递归依赖须固定 commit/实际下载字节 hash、许可证、构建工具、编译参数、运行 DLL 和 adapter/helper 入口；发布物也须固定 hash。不能用本机碰巧存在的 exe、未 pin 的 master/main、联网自动安装或现场学习代替。要取得工具，先列准确来源/版本/hash/许可证、下载量、D 落点及解压/编译/缓存/最终保留预算，请用户批准；材料不齐不安装。

另批软件实验只在全新自有 D 根，使用独立预期的确定性合成 VHDX/ext4/索引真字节或经授权取得的固定公开非业务样本；不利用安装的 Docker/WSL 生成样本，也不从原盘复制。覆盖冗余头/校验、活动日志、offset/整数越界、循环、未知特性、外部依赖、截断和损坏索引。样本生成和预期不能调用被测解析器当 oracle。

必须在语义读取前可靠判定恢复要求。[VHDX 日志规范](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-vhdx/0d588e33-23a6-4c71-b27f-87d97ac3e914)要求处理非空日志；本路线遇到它即拒绝，不能跳过解析旧视图。[ext4 文档](https://docs.kernel.org/admin-guide/ext4.html)也指出 ro 挂载可能回放且不回放可能不一致。故既不挂载，也不采用 RAM overlay/副本恢复视图来取得通过。

资格验证沿用既定上限，不以候选库需要为由自动扩大：120000ms、解析工作集268435456字节、两盘物理读取合计536870912字节（包括重读）、单逻辑 metadata 文件1048576字节/合计16777216字节、100000结构节点、报告262144字节。预算必须覆盖被选读取链实际使用的 buffer/cache/helper，不以“传入了参数”代替约束证明；不将不同含义的进程内存指标冒充工作集硬上限。无法执行限制就不合格。

在自有样本测试越界/重读计费、取消/超时后 helper 完整退出、第二盘失败释放已取资源、未知格式从不判空，以及数据页/错误/通知含敏感哨兵时 stdout/stderr/报告不泄露。数据访问仅允许 broker 明确给出的合成只读输入，额外数据 open/write/mount/replay/repair 请求均为0；工具、已固定依赖和必要系统运行时的只读加载另列准确清单，不把正常 DLL 加载算成业务读盘，也不借其放宽数据路径或 C 盘写入。原生通知、错误栈或 debug 输出不得先落磁盘再脱敏。

未来原盘授权须说明结构/索引物理页可能夹带敏感字段；最小字段解码不等于物理零触及。禁止主动定位/解码/输出 credential、Env、命令或 secret，不保存原始页、数据库副本及持久读缓存；无法做到最小化就拒绝，不能通过全盘导出来补布局。
