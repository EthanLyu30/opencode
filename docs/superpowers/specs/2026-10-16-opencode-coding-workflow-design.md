# OpenCode 非视觉编码工作流设计

**状态：** 2026-10-16 已确认方向；本书面规格待用户审阅，尚未实施。

**所属范围：** Task24B 的第一个生产前置条件，不是付费跑分授权。

**依据：** 保留现有 `visual-build`，另加非视觉编码入口；Kimi 负责规划和判断，DeepSeek 负责主要实现、测试、修复及交付。复用既有可靠执行底座，不重做 Task2–9，不改变租约、重试或预算算法。

## 1. 目标和边界

让库函数修复、后端逻辑、命令行工具等无需页面的任务，也能通过正常生产工作流完成，而不是为跑分临时绕过宿主。

新增工作流类型 `coding-build`；原 `visual-build` 的入口、默认行为、制品、视觉阈值及历史任务解释均保持不变。此阶段不建立可任意编辑的通用 DAG 平台，也不根据提示词猜测是否应跳过视觉检查。

Task24 的非视觉 guardrail 任务使用 `coding-build`；私有页面、Design2Code 和 SWE-bench Multimodal 视觉主任务继续使用 `visual-build`。Chart.js 等库项目若属于视觉主任务，仍须真实构建可复现页面、截图并接受原有视觉评测，不能改成非视觉任务来取得合格结果。

## 2. 显式入口与不可变接纳

- 新增 Location 绑定的 `POST /api/workflow/coding-build`，由现有鉴权、中间件和幂等请求机制保护。
- CLI 新增 `workflow run --kind coding`；省略 `--kind` 仍走原视觉入口。编码入口拒绝视觉预算、预览 URL 和客户端提供的内部冻结计划。
- 请求包含提示词、现有工作流预算、有限修订次数及受信任的本地检查配置，不开放 provider/model/base URL 等绕过模型目录的字段。
- 接纳时冻结 Location、工作流类型、角色路由、检查配置及配置文件哈希、阶段图和预算。幂等键绑定全部语义；不同类型或不同检查配置不能复用同一请求身份。
- 在持久化成功之前不启动模型或命令；接纳后按既有后台执行、取消、恢复、审批及 Responses 查询机制工作。

## 3. 阶段与模型职责

固定流程：工程方案 → 拆解 → 实现 → 实测 → 代码复审 → 按需修复及重新实测/复审 → 交付。

| 编码角色      | 职责                                                   | 模型路线                                 |
| ------------- | ------------------------------------------------------ | ---------------------------------------- |
| `design`      | 目标、约束、接口、风险和验收方案，不生成页面截图       | 已确认的 Kimi 旗舰，Chat，max            |
| `decompose`   | 文件范围、依赖有向无环图和可检查的任务清单             | 同一 Kimi 选择，Chat，high               |
| `implement`   | 按方案修改真实 Location 中的源码                       | 已确认的 DeepSeek Pro，Responses，max    |
| `test`        | 解读宿主真实执行的检查结果；不得把模型声明当成测试证据 | 已确认的 DeepSeek Flash，Responses，high |
| `code_review` | 根据源码变更、方案及实测证据做结构化复审               | 同一 Kimi 选择，Chat，max                |
| `repair`      | 修复失败检查和阻塞复审问题                             | 同一 DeepSeek Pro 选择，Responses，max   |
| `deliver`     | 交付变更清单、检查结果和已解决/遗留问题                | 同一 DeepSeek Pro 选择，Responses，high  |

编码角色和制品合同独立于旧视觉合同。`code_review` 不冒充 `visual_review`，不产生截图或虚假的视觉通过记录。

生产模型仍遵守“自动发现、确认启用、现有任务锁定”，不自动换模、不回退到 Kimi 2.x、不回退协议。编码路由取自当前已确认的模型家族选择，复审要求文本推理和结构化输出，不假设图片输入能力。未核验的模型合同按现有审批/不可用机制停止。

旧七角色模型快照仍按原版本解码，不因新角色增加必填键而失效。新的编码快照明确标识工作流及合同版本，记录每一角色的模型、协议、适配合同和指纹；恢复不能从“当前最新模型”重新选择。Task24 实验另按新 campaign seal 固定模型和运行时，不在同一实验内追踪最新模型。

## 4. 真实工作区与检查宿主

复用现有 Location 文件边界、工具权限、命令沙箱、进程归属及恢复机制。Kimi 的方案、拆解、复审角色只读；只有实现/修复角色获得任务范围内的源码写权限。测试和交付不因新增入口而扩大源码写权限。

本阶段检查配置只支持受信任的 Bun 检查档案：`bun test` 或 `bun run test` 为必选测试项，`bun run build` 和 `bun run typecheck` 可按项目档案显式选用。配置只允许 Location 内的相对工作目录和上述命令类型，不接受任意 shell 字符串、任意可执行文件、远程 URL 或模型临时指定的检查命令。

检查档案在接纳时校验项目配置、冻结命令及其配置哈希；恢复时重新验证。配置漂移不能静默执行新命令。模型工具和项目脚本只在既有受控沙箱中执行；测试脚本不因名称被允许而获得宿主机或网络权限。超时、取消及进程死亡沿用现有归属证明和保守恢复策略。

宿主记录真实命令、退出状态、超时、受控日志和被测试源码指纹。未适用的 build/typecheck 明确记为“不适用”，不能伪造执行成功。无页面任务不启动预览、浏览器或截图进程。

## 5. 制品及成功条件

新增工程方案、代码复审及编码交付合同；已有分解、实现、测试记录仅在语义一致时复用，不为满足旧视觉字段伪造图片哈希。

- 工程方案包含目标、约束、接口/文件范围、风险、验收条件及检查档案引用。
- 分解清单的任务身份唯一，依赖存在且无环，文件路径限于 Location。
- 代码复审记录修订号、源码/实现和实测证据指纹、`pass/revise`、结构化问题及阻塞状态；它不是独立跑分器，也不能替代真实测试。
- 编码交付绑定最终实现、测试及代码复审制品，无必填 `visualReviewSha256`。
- 每次阶段交接均校验工作流、Location、修订及依赖哈希；旧修订、其他任务或仅由模型声称的证据不能用于通过。

实际检查失败时进入有界修复，不先索取“复审通过”来覆盖失败。只有同一最终修订的必选实测全部通过、代码复审通过、无未解决阻塞问题，且预算/权限/制品检查通过，才能交付成功。修订次数耗尽仍未通过则失败，不交付假成功。

## 6. 复用与兼容要求

Schema 定义新请求/制品；Core 负责接纳、编码阶段语义及证据校验；Server 负责真实宿主组合；Protocol/Client/CLI 只暴露正常受保护入口。依赖方向维持仓库约定，客户端由生成器更新。

新类型按自身合同接入执行器和结算检查。旧类型仍走旧合同，不能让通用 `workflow.create` 伪造编码接纳证明来获得工具权限。底层事件存储、租约 fencing、持久化预算、重试及取消算法保持原样；新增类型的必要分发与合同验证不构成绕过这些底座。

已有视觉任务、模型启用选择和已部署版本不随源码修改自动改变。该入口经验证、提交及 push 后，只有显式重新构建部署才进入本地可执行程序；旧 `dist`、历史 seal 和回滚制品不覆盖。

## 7. 零额度验收

以本地录制/假 provider 和真实临时工作区验证，禁止读取真实 `.env.local`、请求真实 `/models` 或发出付费调用。任务专用数据、缓存和临时文件全部在 D 盘。

必须覆盖：

1. 没有 `index.html`、预览或浏览器的库修复能按完整编码流程完成；设计/拆解/复审由假 Kimi 路线、实现/测试/修复/交付由相应假 DeepSeek 路线执行。
2. 真正错误实现先测试失败，修复后再通过；空测试结果、错误源码指纹或模型自报通过都不能成功。
3. 代码复审要求修订时进入修复；到达修订上限、预算耗尽或阻塞问题未解决时不得交付。
4. 崩溃恢复保留模型和合同快照；已结算阶段不重复请求，未明确结算的请求不被当成可免费重放。
5. 幂等重试、取消、审批、REST/SSE 重放及 Responses 关联在新类型上保持一致。
6. 越界路径、链接逃逸、检查配置漂移、跨任务/跨修订制品、伪造内部接纳字段和权限升级被拒绝。
7. 旧视觉入口及历史七角色快照回归通过，默认 CLI 行为和已有算法不变。

运行受影响包测试及类型检查，生成客户端并验证稳定性；对最终准确的构建产物再次做零额度验收。只有已运行并通过的部分可标为完成。

## 8. 与后续 Task24B 前置工作的关系

此规格完成后仍需单独落实以下工作，不把“入口能跑”宣称为“工作流已证明有效”：

- 库项目评测适配：内容寻址的依赖/构建档案、独立隐藏功能测试及视觉主任务的可复现页面；所有实验组使用同一公开夹具和隐藏评测器。反向应用标准补丁成功不能替代真实功能测试。非视觉 guardrail 单独统计功能和安全结果，不套用视觉 75/65 门槛或伪造视觉分数。
- 真实 pilot 执行循环：通过现有 broker、持久化队列和证据链实际执行五组，而非只规划数据库行；保留严格的两个币种上限、逐请求预留与结算、未知用量保守处理及停止机制。三任务各组一次，严格 15 个 cell。
- 新 seal 和 Task24A：冻结新源码、准确的修改版/官方二进制、任务、公开夹具、评测器、模型及预算，重跑零额度验收。旧 seal 只作历史记录。
- 付费门槛：由用户另行批准基于当时官方价格的 Kimi CNY 和 DeepSeek USD 上限后才可开始 Task24B；此规格及“继续实施”均不授权消费。

本规格审阅后再写对应实施计划，沿用直接在 `dev` 开发、验证后提交并 push `fork/dev` 的方式。后续评测/执行循环的具体书面规格必须与本入口合同对齐，不能通过改任务类别或降低评分门槛来迁就宿主。
